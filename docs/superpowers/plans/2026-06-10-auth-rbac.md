# Database-Driven Authentication & RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement a secure, offline-first, database-driven authentication and role-based access control (RBAC) system for FSRMS, decoupled from Supabase Auth for cashier accounts.

**Architecture:** Custom password hashing using PBKDF2/SHA-256 (Web Crypto API) with unique salts per user. Local sessions cached in IndexedDB and persisted in localStorage. Role-based client-side routing, Sidebar filtering, and RLS preservation via generic device-level Supabase Auth accounts.

**Tech Stack:** React, TypeScript, IndexedDB (idb), Web Crypto API, PostgreSQL (Supabase)

- [ ] **Step 1: Implement password hashing with Web Crypto API**
  Write the PBKDF2/SHA-256 password hashing logic in `src/utils/crypto.ts`.
  ```typescript
  export function generateSalt(length: number = 16): string {
    const array = new Uint8Array(length);
    window.crypto.getRandomValues(array);
    return Array.from(array)
      .map(b => b.toString(16).padStart(2, '0'))
      .join('');
  }

  export async function hashPassword(password: string, salt: string): Promise<string> {
    const encoder = new TextEncoder();
    const passwordBuffer = encoder.encode(password);
    const saltBuffer = encoder.encode(salt);

    const baseKey = await window.crypto.subtle.importKey(
      'raw',
      passwordBuffer,
      { name: 'PBKDF2' },
      false,
      ['deriveBits', 'deriveKey']
    );

    const derivedBits = await window.crypto.subtle.deriveBits(
      {
        name: 'PBKDF2',
        salt: saltBuffer,
        iterations: 100000,
        hash: 'SHA-256'
      },
      baseKey,
      256
    );

    return Array.from(new Uint8Array(derivedBits))
      .map(b => b.toString(16).padStart(2, '0'))
      .join('');
  }
  ```

### Supabase RLS Hardening Backlog & Technical Debt

> [!WARNING]
> **Technical Debt - Database RLS Hardening Pending**: Row-Level Security (RLS) is currently NOT enabled on the Supabase project. The current database security relies solely on client-side RBAC and application logic. We must NOT assume that the database is secure based solely on frontend RBAC constraints.

To ensure database-level security after the stabilization of RBAC, the following backlog items are created for a dedicated **Security Hardening Phase for Supabase RLS**:

- [ ] **Backlog 1: RLS Activation**
  Enable Row-Level Security on all database tables (specifically `users`, `transactions`, `customers`, `cash_shifts`, and `appointments`).
- [ ] **Backlog 2: `users` Table Policies**
  Implement strict read/write policies on the `users` table:
  - Cashiers can read only their own profile.
  - Owners can perform full CRUD (read, write, delete) on all profiles.
  - Unauthenticated/anonymous users can read only salts but never hashes.
- [ ] **Backlog 3: Owner/Cashier Access Policies**
  - Limit cashier write operations (transactions, shifts) to cashier-owned records.
  - Prevent cashiers from editing or deleting transactions (void operations restricted to Owner).
- [ ] **Backlog 4: Sync-Engine Service Policies**
  - Establish PostgreSQL RLS policies for the sync-engine to ensure offline-queued mutations are processed under correct access constraints.
- [ ] **Backlog 5: Dedicated Security Hardening Phase**
  - Perform a full security audit and verification of RLS policies once RBAC is completed and stabilized.
